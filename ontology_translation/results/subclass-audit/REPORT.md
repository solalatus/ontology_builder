# Subclass audit across the five domains (issue #155)

Generated by `tools/subclass_audit_report.py` from `audit.json` (computed by
`tools/subclass_audit.py`), `classification.yaml` (a reviewer's judgment, one line per pair)
and `recovered-connectivity.json` (computed by `tests/evals/subtype-connectivity.mjs`).
Do not edit by hand; rerun the scripts instead.

## Question

#155 asks, for every domain and not just FIBO: if the compiler were allowed to emit a
label-only `specializes` edge, which source `rdfs:subClassOf` edges would newly become
translatable, and would any domain need re-translation? Underneath that sits the
design question: are these subtypes real kinds that need an edge, or something a flat
model already expresses better (a property value, a state)?

## Method

- **Inputs, all committed:** the original sources under `domains/<id>/source/`
  (checksum-pinned by each `source-manifest.yaml`, provenance in `PROVENANCE.yaml`), each
  domain's `translation.json` (which source IRI became which target element) and
  `reference.domain.yaml`. itops has no RDF source; its subclass edges are the 23 `"is a"`
  predicates of the original MTSR fixture (`domains/itops/source/itops_mtsr.original.yaml`),
  removed from the ground truth on 2026-07-29.
- **Walk:** for each source IRI mapped to a target class X, follow `rdfs:subClassOf`
  upward (named classes only; OWL restrictions are property constraints, not taxonomy)
  through IRIs that were not translated, and stop at the first translated ancestor. If it
  became a different class Y, `X specializes Y` is a **candidate pair**.
- **Identity:** an IRI's identity is what the mappings listing it *first* say it became.
  The compiler also cites supporting evidence further down `source_iris`, often the
  parent class (iof-supply-chain's `Trailer` cites `[Trailer, Container]`); counting those
  produced nonsense pairs such as `Trailer specializes Wagon`, so they are reported, not
  walked.
- **Connectivity**, measured in the current reference model: an *island* has no
  relationships at all; *not connected to parent* means no chain of relationships links
  the subclass to its parent, so a `specializes` edge would join two separate parts of
  the model. That is the problem #155 describes.
- **Classification** (`classification.yaml`, judgment, not computed):
  - **kind**: rigid, with relationships, properties or rules of its own.
  - **value**: rigid, but differs from its siblings by one attribute (medium, mode, type
    flag); a controlled-value property on the parent says the same.
  - **state**: an instance enters and leaves it (declared, accrued, degraded).
  - **role**: held because of a relationship.
  - **individual**: names one real-world thing, not a type.

### Connectivity under three options

Connected components of each reference model (relationships taken as undirected):

- **now**: the model as committed.
- **+ kind edges**: add `specializes` only for pairs classified as kinds.
- **+ kind edges, fold value/state**: additionally turn each value or state subtype into a
  value of a controlled property on its parent, removing that class.

Folding a subtype merges it into its parent, which joins their components exactly as an
edge would; the difference is that the model gets smaller rather than gaining a new
construct.

## Findings

1. **FIBO is the real case, and it is fragmented regardless of subclassing.** Its reference model has 28 components; the largest holds 24 of 57 classes. 22 of its 24 subclasses are not connected to their parent. The 8 kinds among them (CollateralizedLoan, InterestPaymentTerms, InterestRateReset, InterestRateSettingEvent, PrepaymentTerms, PrincipalRepaymentTerms, RevolvingLineOfCredit, SecuredLoan) are where a `specializes` edge would add information a property cannot.
2. **itops shows what dropping "is a" cost.** All original "is a" links still have both classes in the model, and no subclass is an island, but 6 are no longer connected to their parent. The model has 3 components; the 2 outside the main one are {ContainerPlatform, DataCentre, Server, VirtualMachine}; {Endpoint, NetworkDevice, NetworkSegment}. With the kind edges restored it has 1. 5 of the original links (IncidentResponseTeam, ItOperationsTeam, NetworkOperationsCentre, SecurityOperationsCentre, ServiceDesk) make an organisational unit a subclass, though each names one unit in the bank.
3. **Brick's candidates are all values** (sensors and setpoints by medium, substance or mode). Brick also has the most untranslated subtypes of translated classes (165), so an unguarded rule would pull in a long tail of value subclasses on re-translation.
4. **States would be modelled wrongly as subclasses** (6 pairs: AccruedInterest, CybersecurityIncident, DegradedState, FailedState, MajorIncident, OperatingState). An asset is not permanently a `FailedState`, and an incident is declared major and later de-escalated. Any `specializes` rule needs a guard that rejects these.
5. **Translation artefacts found along the way:**
   - brick-hvac: `Building`, `Floor`, `Zone` reach `Space` only through an IRI that `Space`'s mapping cites second (e.g. Building -> Location -> Space). They hold only under the translation's merged reading, so they are not counted. In Brick, `Building`, `Floor` and `Zone` sit under `brick:Location`, which sits under `rec:Space`, beside `brick:Space` rather than under it; the translation merged `brick:Space` and `rec:Space` into one `Space`.
   - Class mappings that cite a parent class as evidence (iof-supply-chain's `Trailer` cites `[Trailer, Container]`) are handled by the first-listed rule and no longer affect the result.

## What the reference audit supports

This part covers the *reference* models; the next section covers the interview outputs.

- **An unguarded `specializes` rule is not justified.** 37 of 68
  candidates are values or states that a flat model already expresses, and every domain
  would need re-translation.
- **A guarded rule (kinds only) has a real but narrow case**: 25 pairs, of which
  15 actually join separate parts of a model (fibo-loans, iof-supply-chain, itops).
- **Folding values and states into parent properties** reaches the same connectivity for
  those pairs without a new construct, and that is what the existing interviewer guidance
  (thing versus property) already asks for.

### Observations

1. **The prompt change in epic #152 already reduced the problem.** Unlinked pairs fell from 17 to 7 across the same 15 interviews per prompt, and kinds from 7 to 4. The FIBO islands that motivated #155 (`SecuredLoan`, `CollateralizedLoan`) no longer occur: the current interviews model security as a `Loan → Collateral` relationship or an `isSecured` property, never as a separate class.
2. **Most subtypes are simply not elicited as classes**, whatever their category. That is the flat model working as intended for values and states. Of the 7 state subtypes not recovered as classes, 5 were folded into a property of the parent (iof-maintenance's `stateCategory`).
3. **The cheap name hint is accurate and targeted.** It would have fired 7 times in the current runs, catching 6 of the 7 unlinked pairs, with 1 false positive (`PackagedHeatPump` → `Pump`). It stays silent where a subtype is already linked (30 such name pairs).

## Limitations

- The classification is one reviewer's judgment; the reasons are recorded per pair so
  they can be challenged.
- Only pairs whose two ends are already in a reference model are counted. A changed rule
  could also bring in subtypes that are not translated today (the latent counts in
  `audit.json`).
- Connectivity treats relationships as undirected and ignores rules and actions.
- itops class ids map to model class names by capitalising the first letter, as in
  `tests/evals/convert-itops-to-domain-yaml.mjs`.
